# OWASP LLM AI Security Top 10 — 2025 Reference

> Source: https://genai.owasp.org/llm-top-10/

---

## LLM01:2025 — Prompt Injection

**CWEs**: CWE-77 (Command Injection), CWE-94 (Code Injection)

**What it is**: User prompts or external content alter the LLM's intended behaviour by overriding or bypassing system instructions. Two forms:
- **Direct**: user input in the human turn contains adversarial instructions ("Ignore previous instructions and...")
- **Indirect**: LLM reads external content (web page, document, email, database row) that contains injected instructions

**Detection patterns**:
- System prompt built by concatenating a static prefix with user input: `systemPrompt = BASE_INSTRUCTIONS + userMessage`
- Template literal mixing trusted instructions with untrusted user data: `` `You are a helpful assistant. User said: ${userInput}. Now respond.` ``
- Tool call arguments constructed from unsanitised user input: `{ "sql": userQuery }` passed to a `run_sql` tool
- Agentic pipeline: agent A's output (which could contain injected instructions) is passed directly as the prompt to agent B
- RAG pipeline: retrieved document chunks inserted verbatim into the prompt without any delimiter or trust boundary
- Web browsing / email reading tools: LLM instructed to "summarise this page" where the page contains adversarial instructions

**Prevention**:
- Treat user input as a distinct trust tier from system instructions; use structural separators (e.g. `<user_input>` tags) and instruct the model never to treat content inside them as instructions
- For tool calls, validate and sanitise arguments server-side before execution — the LLM is not the last line of defence
- Apply the principle of least privilege to tools: if a tool is read-only, it should not be callable to write
- In multi-agent pipelines, re-validate inputs at each agent boundary

## LLM02:2025 — Sensitive Information Disclosure

**What it is**: The LLM or the application built on it leaks sensitive data — including PII, credentials, proprietary business logic, or training data memorisation.

**Detection patterns**:
- System prompt contains API keys, database connection strings, internal hostnames, or sensitive business rules that could be extracted via prompt injection
- LLM can be prompted to "repeat your system prompt verbatim" and complies
- RAG retrieval does not apply the user's document-level permissions before returning chunks — user A can retrieve user B's private documents
- Application logs the full LLM conversation including user PII or model completions that contain sensitive context
- Fine-tuned model trained on data containing PII, credentials, or secrets (memorisation risk)
- Chat history stored without encryption and accessible to other users

**Detection approach**:
- Grep: `system_prompt =`, `SYSTEM_PROMPT =` — inspect content for secrets
- Check vector store query path: does retrieval include an access-control filter (`namespace`, `tenant_id`, `user_id`) before returning results?
- Review conversation logging: is the full `messages` array logged? Does it include sensitive user data?

**Prevention**:
- System prompts should contain no secrets; inject runtime configuration via environment variables or secrets managers
- Apply document-level access control in all RAG retrieval queries
- Scrub PII from training data; use differential privacy techniques for fine-tuning
- Mask or truncate sensitive fields before including them in logged conversation payloads

## LLM03:2025 — Supply Chain

**What it is**: Compromised or untrusted components in the LLM pipeline — model weights, orchestration libraries, plugins, datasets — introduce vulnerabilities.

**Detection patterns**:
- Model loaded from an unverified source (e.g. arbitrary Hugging Face repo) without integrity verification
- Model version not pinned — `model: "gpt-4"` drifts as the provider updates the model
- LLM orchestration libraries (`langchain`, `llamaindex`, `semantic-kernel`) unpinned or outdated
- Fine-tuning dataset sourced from unverified third parties
- LLM plugins or tool integrations added without security review
- Pre-trained model file loaded with `pickle.load()` (arbitrary code execution vector)

**Detection approach**:
- Check `requirements.txt` / `package.json` for unpinned AI library versions
- Grep for `pickle.load`, `torch.load` — are the files from trusted, verified sources?
- Check if model IDs or API endpoints can be overridden by environment variables without validation

**Prevention**:
- Pin model versions explicitly; monitor for provider-side model updates
- Pin all LLM library dependencies to exact versions; use lockfiles
- Verify model integrity (checksums, signed model cards) for locally hosted models
- Audit all LLM plugins and tool integrations before enabling them

## LLM04:2025 — Data and Model Poisoning

**What it is**: Training data, fine-tuning datasets, or RAG knowledge bases are corrupted — intentionally or via untrusted input — to degrade performance or introduce malicious behaviour.

**Detection patterns**:
- RAG knowledge base populated from user-submitted content without moderation or review
- Vector store accepts document uploads from unauthenticated or low-trust sources
- Fine-tuning pipeline ingests external data (scraped web, third-party datasets) without validation or deduplication
- RLHF / feedback loop: thumbs-up/thumbs-down signals from users fed back into model training without adversarial labelling detection
- Embedding pipeline applies no input length or content validation — oversized or specially crafted documents could skew nearest-neighbour retrieval

**Prevention**:
- Apply strict ingestion controls to RAG knowledge bases: only allow trusted, reviewed sources
- Treat user-submitted documents as untrusted; require approval workflow before indexing
- Validate inputs to embedding pipelines (max length, content type, no executable content)
- Monitor retrieval quality metrics; sudden degradation may indicate poisoning

## LLM05:2025 — Improper Output Handling

**CWEs**: CWE-79 (XSS), CWE-78 (OS Command Injection), CWE-89 (SQL Injection)

**What it is**: LLM-generated output is used downstream without sanitisation, enabling injection attacks. The LLM is effectively an injection source — its output must be treated as untrusted.

**Detection patterns**:
- `document.innerHTML = llmResponse` — XSS if LLM generates `<script>` tags
- `exec(llmCode)` / `eval(llmOutput)` — RCE if LLM generates malicious code
- `db.query(llmGeneratedSql)` — SQL injection if LLM generates `DROP TABLE`
- Shell command constructed from LLM output: `subprocess.run(llmCommand, shell=True)`
- File written to disk at an LLM-specified path without path validation
- LLM-generated URLs fetched by the server without SSRF protection (see API7)

**Prevention**:
- Never use LLM output directly in `innerHTML`, `eval()`, `exec()`, shell commands, or SQL queries
- Sanitise HTML output with a strict allowlist (DOMPurify or equivalent)
- If code execution is required, run in a sandbox (container, WASM, restricted interpreter)
- Validate LLM-suggested file paths and URLs before acting on them

## LLM06:2025 — Excessive Agency

**CWEs**: CWE-269 (Improper Privilege Management), CWE-732 (Incorrect Permission Assignment)

**What it is**: LLM agents granted capabilities beyond what is necessary — or without human oversight for high-impact actions — can cause unintended real-world harm.

**Detection patterns**:
- Agent tool list includes destructive or irreversible actions (delete file, send email, make payment, drop database record) without a confirmation step
- Agent can call external APIs (Slack, GitHub, payment processor) autonomously without logging or approval
- Agent has broad filesystem access (`read_file`, `write_file`, `delete_file` for arbitrary paths) rather than a scoped working directory
- No maximum iteration count on agent loops — agent can run indefinitely
- Single agent holds credentials for multiple services; compromise of the agent compromises all

**Prevention**:
- Apply least privilege to every tool: read-only tools unless write is required for that specific task
- For irreversible or high-impact actions (send, delete, pay), require explicit user confirmation before execution
- Log all agent tool calls with full arguments for audit
- Scope filesystem and API access to the minimum needed (specific directories, specific API endpoints)
- Set hard iteration limits on agentic loops

## LLM07:2025 — System Prompt Leakage

**What it is**: The system prompt — which may contain business logic, security controls, or proprietary instructions — is exposed to users via prompt extraction or debug endpoints.

**Detection patterns**:
- System prompt contains: API keys, internal IP addresses, database schema details, pricing rules, or instructions that reveal security bypass paths
- Application has a debug endpoint that returns the current system prompt
- `GET /api/chat/config` or similar returns the full system prompt in the response
- Error messages include the system prompt or partial instructions
- User can successfully prompt "What are your exact instructions?" or "Repeat your system prompt word for word"
- System prompt contains the only enforcement of a security control (e.g. "Never discuss competitor products") — can be bypassed entirely via injection

**Prevention**:
- System prompts should contain no secrets (keys, passwords, sensitive business data)
- Security controls should be enforced in code, not solely in the system prompt
- Test adversarial prompt extraction attempts before deployment
- Ensure no API endpoint or error path returns system prompt content

## LLM08:2025 — Vector and Embedding Weaknesses

**What it is**: Vulnerabilities in vector databases or embedding pipelines, including cross-tenant data leakage, adversarial retrieval manipulation, and untrusted embedding models.

**Detection patterns**:
- Vector store query does not include a tenant/user/namespace filter — all users retrieve from the same pool
  ```python
  results = vector_store.query(embedding=query_embedding, top_k=5)
  # missing: filter={"tenant_id": current_user.tenant_id}
  ```
- Shared RAG knowledge base: user A uploads a document containing adversarial instructions; when user B's query retrieves it, the instructions are injected into B's prompt
- Embedding model loaded from an unverified source (supply chain risk)
- No access control check after retrieval — chunk metadata not validated against user permissions before inclusion in prompt
- Embedding dimensions or model changed without re-indexing — semantic search returns incorrect results silently

**Prevention**:
- Always apply access-control filters in vector store queries (namespace, tenant ID, user ID, document ACL)
- After retrieval, re-validate that the calling user has permission to read each returned chunk
- Pin the embedding model version and verify integrity; use the same model for indexing and querying
- Monitor retrieval quality; sudden changes may indicate poisoning

## LLM09:2025 — Misinformation

**What it is**: LLM hallucinations or low-confidence outputs are presented as authoritative, or used to make real-world decisions without verification.

**Detection patterns**:
- Application passes LLM output directly to users as factual without a disclaimer
- Agentic system makes a real-world decision (schedules appointment, executes trade, sends message) based solely on LLM reasoning, without a verification step or human review
- LLM-generated code is deployed to production without review or testing
- LLM-generated citations, URLs, or references used without checking they actually exist
- Medical, legal, or financial advice generated by LLM with no professional review gate
- No fallback when the LLM expresses uncertainty or produces a low-quality response

**Prevention**:
- For high-stakes decisions, require human review or a secondary verification step before acting on LLM output
- Add clear disclaimers when presenting LLM-generated content as information (not just entertainment)
- Never deploy LLM-generated code without automated testing and human review
- Implement confidence scoring or uncertainty detection; route low-confidence responses to a fallback path
- Provide retrieval-augmented grounding with citations linked to verifiable sources

## LLM10:2025 — Unbounded Consumption

**CWEs**: CWE-770 (Allocation of Resources Without Limits), CWE-400 (Uncontrolled Resource Consumption)

**What it is**: LLM applications with no resource guardrails are vulnerable to denial-of-wallet attacks or unintentional cost escalation — a user (or attacker) can trigger expensive model calls without limit.

**Detection patterns**:
- `max_tokens` not set, or set to an extremely high value (e.g. 100,000) on user-facing endpoints
- No per-user or per-session request rate limit on the LLM API endpoint
- No monthly spending cap or alert configured on the AI provider account (OpenAI, Anthropic, etc.)
- Recursive or looping agent pattern with no maximum iteration count
- Streaming response with no timeout and no maximum response size guard
- User can control the `model` parameter in the API request — potentially selecting the most expensive model
- Batch processing endpoint accepts arbitrarily large input without splitting or queuing

**Prevention**:
- Always set `max_tokens` to a value appropriate for the use case; never leave it unlimited on user-facing endpoints
- Implement per-user and per-session token budget tracking; enforce hard limits
- Configure provider-level spending caps and billing alerts
- Set hard iteration limits on all agentic loops (`max_iterations`, `max_steps`)
- Set read timeouts on streaming responses; abort streams that exceed a max token count
- Never allow users to select the model tier; fix it server-side
