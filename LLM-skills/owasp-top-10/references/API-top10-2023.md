# OWASP API Security Top 10 — 2023 Reference

> Source: https://owasp.org/API-Security/editions/2023/en/0x11-t10/

---

## API1:2023 — Broken Object Level Authorization (BOLA / IDOR)

**CWEs**: CWE-285, CWE-639

**What it is**: Every API endpoint that receives an object ID from the client and performs an action on that object must validate that the requesting user has permission to access *that specific record*. Comparing session user ID against the ID parameter is necessary but not sufficient; ownership hierarchy must be validated.

**Detection patterns**:
- Route handler accepts `req.params.id`, `req.query.id`, or body `id` and passes it straight to a DB query
- `WHERE id = $1` without a corresponding `AND user_id = $currentUser`
- GraphQL mutations accepting `reportKeys: [ID]` or `deleteReports(id: ID!)` with no ownership re-check
- REST: `GET /shops/{shopName}/revenue_data.json` — iterating a user-controlled ID parameter returns other users' records
- BOLA differs from BFLA: the user is *allowed* to call the endpoint, but is accessing an *object* they don't own

**Prevention**:
- Always validate ownership: `SELECT * FROM records WHERE id = $1 AND owner_id = $currentUser`
- Prefer UUIDs over sequential integers for record IDs (harder to enumerate)
- Write automated tests that verify one user cannot access another user's records

## API2:2023 — Broken Authentication

**CWEs**: CWE-204, CWE-307

**What it is**: Authentication mechanisms implemented incorrectly allow attackers to compromise tokens or exploit implementation flaws to assume other users' identities.

**Detection patterns**:
- No rate limiting or lockout on `/login`, `/forgot-password`, `/reset-password`, `/verify-otp`
- Credentials or tokens visible in URL query string (`?password=`, `?token=`, `?key=`)
- `{"alg":"none"}` accepted in JWT header
- JWT expiry (`exp`) claim not validated
- Plain text, MD5, or SHA1 password storage
- Microservices calling each other without any auth token
- GraphQL batching: multiple `mutation { login(...) }` in one request array bypasses per-request rate limits
- `PUT /account { "email": "..." }` without requiring current password confirmation

**Prevention**:
- Rate limit and lock out auth endpoints with stricter limits than general API endpoints
- Require re-authentication for sensitive operations (email change, password change, 2FA update)
- Validate JWT signature, algorithm (allowlist only `RS256`/`ES256`/`HS256`), and `exp`
- Use standard auth libraries — don't hand-roll token generation or password storage

## API3:2023 — Broken Object Property Level Authorization

**CWEs**: CWE-213, CWE-915

**What it is**: Combines *excessive data exposure* (API returning fields the user shouldn't see) and *mass assignment* (user setting fields they shouldn't be able to set).

**Detection patterns**:

*Excessive data exposure (read side)*:
- Serialiser calls `model.toJSON()`, `to_dict()`, `.serialize()`, or returns `SELECT *` without an explicit field whitelist
- Response includes fields like `password_hash`, `internal_notes`, `stripe_customer_id`, `is_staff` that clients don't need
- GraphQL resolvers returning full object when only a subset of fields are requested

*Mass assignment (write side)*:
- `Object.assign(record, req.body)` / `record.update(req.body)` / `model.create(req.body)` without an explicit permitted-attributes list
- Fields like `role`, `isAdmin`, `balance`, `creditLimit`, `blocked`, `verified` present in request body schema with no server-side filter
- Scenario: `POST /api/host/approve_booking` with `{ "total_stay_price": "$1,000,000" }` modifying a protected field

**Prevention**:
- Cherry-pick returned fields: use DTO/view models rather than serialising the full ORM object
- Explicitly define permitted write fields per endpoint — reject any extra keys
- Validate schema with `protovalidate`/`zod`/`pydantic`/`marshmallow` allowlists

## API4:2023 — Unrestricted Resource Consumption

**CWEs**: CWE-770, CWE-400, CWE-799

**What it is**: API requests consume bandwidth, CPU, memory, storage, or paid third-party calls without limits, enabling DoS or cost inflation.

**Detection patterns**:
- Pagination `limit` / `page_size` parameter with no server-side cap (user requests 100,000 rows)
- GraphQL: no query depth limit, no query complexity limit, no operation count limit per request (batching)
- File upload endpoint: no maximum file size enforced before processing
- Image thumbnail generation triggered for each upload without rate limit or concurrency cap
- `POST /initiate_forgot_password` with no rate limit → attacker triggers thousands of SMS sends billed per request
- No execution timeout on long database queries or external API calls
- Third-party provider spending limit not configured; no billing alert

**Prevention**:
- Hard-cap all user-controlled numeric parameters server-side (pagination, batch size, result count)
- Set query depth + complexity limits in GraphQL middleware
- Rate limit per-user and per-IP, with stricter limits for operations that trigger outbound costs
- Configure spending limits and alerts for every paid third-party integration
- Set execution timeouts and memory limits on request handlers

## API5:2023 — Broken Function Level Authorization (BFLA)

**CWEs**: CWE-285

**What it is**: Complex role hierarchies lead to auth checks being missed on administrative or sensitive functions.

**Detection patterns**:
- Admin endpoint (`/api/admins`, `/api/users/export_all`, `/api/invites/new`) lacks role check
- HTTP method manipulation: `GET /api/resource/{id}` exists with auth; `DELETE /api/resource/{id}` shares the handler but skips the role check
- `POST /api/invites/new` accepts `{ "role": "admin" }` without verifying the caller is an admin
- Endpoint URL guessing: `/api/v1/users/export` is accessible to regular users
- Admin functions inside regular controllers that rely only on obscure URLs rather than auth checks
- Sub-user or delegated access paths that bypass the primary role check

**Prevention**:
- Default-deny: every function requires an explicit permission grant; no access by default
- All admin controllers must extend/call a shared admin authorisation guard
- Review all endpoints for whether changing the HTTP method bypasses access controls
- Do not rely on URL obscurity — auth must be enforced in code

## API6:2023 — Unrestricted Access to Sensitive Business Flows

**What it is**: APIs expose business-critical flows without compensating for automated abuse — not necessarily a code bug, but a missing design control.

**Detection patterns**:
- Purchase/checkout endpoint: no CAPTCHA, no device fingerprint check, no velocity check (multiple purchases per second from one account)
- Ticket/seat reservation: no per-account or per-session reservation limit
- Referral/reward flow: registration and referral credit can be automated with a script
- "Add to cart" + "complete purchase" reachable in < 1 second by a bot — no human-timing validation
- Voting, rating, or review submission with no per-account rate limit

**Prevention**:
- Identify flows where automated abuse harms the business (scalping, spam, fraud, account farming)
- Protect with: CAPTCHA or biometric signals, device fingerprinting, velocity/frequency limits per account
- For developer/B2B APIs (machine-to-machine), ensure they have equivalent protections
- Non-human pattern detection (e.g. reaching checkout in < 500ms from page load)

## API7:2023 — Server Side Request Forgery (SSRF)

**CWEs**: CWE-918

**What it is**: API fetches a remote resource using a URL supplied by the client without validating it, enabling requests to internal infrastructure.

**Detection patterns**:
- `POST /api/profile/upload_picture { "picture_url": "..." }` — server fetches the URL
- Webhook creation: `{ "url": "http://169.254.169.254/latest/meta-data/iam/security-credentials/..." }` triggers a test request
- File import from URL, RSS feed fetcher, link preview generator, custom OAuth callback — any endpoint that resolves a user-supplied URI
- `fetch(req.body.url)` / `axios.get(params.url)` / `http.Get(userUrl)` without allowlist validation
- Blind SSRF: the response is not returned to the user, but internal state changes (port open/closed timing)

**High-value SSRF targets**:
- `http://169.254.169.254/` — AWS/GCP/Azure instance metadata (credentials, IAM roles)
- `http://10.0.0.0/8`, `192.168.x.x` — internal network services
- `http://localhost:PORT` — local services not exposed externally

**Prevention**:
- Allowlist permitted URL origins and schemes (e.g. only `https://` to a known CDN domain)
- Reject `localhost`, `127.0.0.1`, RFC-1918 ranges, and cloud metadata IPs
- Disable HTTP redirections on the server-side fetch client
- Never return raw third-party responses to the caller

## API8:2023 — Security Misconfiguration

**CWEs**: CWE-2, CWE-16, CWE-209, CWE-319, CWE-444, CWE-942

**What it is**: APIs and supporting infrastructure misconfigured, including CORS, TLS, error responses, and header handling.

**Detection patterns**:
- `Access-Control-Allow-Origin: *` on authenticated endpoints
- HTTP (not HTTPS) used for internal service-to-service communication
- Error responses include stack traces, internal file paths, or DB error messages
- `X-Api-Version: ${jndi:ldap://...}` processed by log4j — JNDI lookup expansion enabled
- `GET /dm/user_updates.json` response missing `Cache-Control: no-store` → private data cached in browser
- Unnecessary HTTP verbs (TRACE, PATCH) enabled on endpoints that only need GET/POST
- S3 bucket / cloud storage with public read or write
- Swagger/OpenAPI UI exposed in production (`/swagger-ui`, `/api-docs`)

**Prevention**:
- Enforce TLS everywhere, including internal traffic
- Restrict CORS to known origins; never use `*` on credentialled endpoints
- Return only generic error messages to clients; log details server-side
- Restrict HTTP verbs per endpoint; disable unused verbs

## API9:2023 — Improper Inventory Management

**CWEs**: CWE-1059

**What it is**: Multiple API versions, undocumented endpoints, and poor visibility of what's running and where.

**Detection patterns**:
- Multiple version prefixes in route files (`/v1/`, `/v2/`, `/v3/`, `/beta/`) with no documented sunset date for old versions
- `beta.api.example.com` runs the same API as production but without the rate limiting applied to the main host
- Debug/health endpoints (`/debug`, `/internal`, `/actuator`, `/metrics`) accessible without authentication
- Swagger UI or full OpenAPI spec reachable in production without auth
- No inventory document mapping API host → environment → who can access it
- Different API versions share the same database, so a deprecated version with weaker security exposes production data

**Prevention**:
- Maintain an API inventory: host, environment, version, access policy, retirement date
- Generate OpenAPI specs in CI/CD; gate on spec drift
- Apply identical security controls to all non-production environments that share production data
- Automate deprecation: return `Sunset` headers; retire old versions on schedule

## API10:2023 — Unsafe Consumption of APIs

**CWEs**: CWE-20, CWE-200, CWE-319

**What it is**: Developers trust third-party API data more than user input and apply weaker validation, letting attackers compromise the target via integrated services.

**Detection patterns**:
- Third-party API response stored directly in a SQL query: `SELECT * FROM businesses WHERE name = '${thirdPartyData.name}'`
- Third-party service compromised and returns `308 Permanent Redirect` to attacker's server; application follows unconditionally and sends sensitive data
- GitHub repo name `'; drop db;--` passed to an SQL query because it was assumed safe
- No timeout on outbound third-party API call → server hangs indefinitely
- Third-party webhook payload fields used in template rendering without sanitisation
- Communicating with third-party APIs over HTTP (not HTTPS)

**Prevention**:
- Validate and sanitise all data received from third-party APIs before using it, exactly as you would user input
- Do not blindly follow redirects from third-party services; maintain an allowlist of redirect destinations
- Set connection and read timeouts on all outbound API calls
- Ensure all third-party API communication uses TLS
- Assess the security posture of third-party service providers before integrating
