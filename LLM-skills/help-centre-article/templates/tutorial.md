# Tutorial template

**Diátaxis quadrant:** Tutorial (learning-oriented).

**When to use:** the reader is meeting a workflow for the first time and needs to be walked from "I've never done this" to "I've done it once and understand the shape of it". Tutorials teach a skill end to end. They are not how-to guides with extra hand-holding — a how-to guide assumes the reader already knows the shape of the workflow.

**What earns a tutorial:** a tutorial earns its shape when the reader is meeting the workflow for the first time and the goal is to *learn the shape*, not to complete a real-world task. The article walks one canonical path end to end, with no choices and no edge cases — choices break the perfect-reliability requirement that lets the reader trust each step worked. If the reader already knows the shape and just needs the recipe, it's a [how-to](how-to.md); if they want the model behind the workflow, it's an [explanation](explanation.md) (use the Explanation article specialisation within if the article is about a single named product object).

**Voice and tone:** warm, second-person, "you'll" and "we'll". The reader is a learner, not a power user. Reassure them that the steps will be specific, that nothing is hidden, and that they don't need prior context. Introduce each term in plain English before using its acronym.

**Structural elements:**

- **Opening:** name the concrete outcome the reader will reach and the skill they will have at the end. One short paragraph. No history, no philosophy, no marketing.
- **Before you start:** prerequisites, with sideways links to the reference or explanation articles the reader may need.
- **Numbered phases or steps** that take the reader through the whole workflow in order. Every step is testable — the reader can see whether it worked.
- **What you've learned:** one short paragraph naming the skill the reader now has. No new information; this is a confidence checkpoint.
- **Next steps:** forward links to the how-to articles or follow-on tutorials the reader will want next.

The Phase / What you've learned / Next steps labels are conventions inspired by Diátaxis. The framework prescribes the *spirit* — show the destination, deliver early results, acknowledge the learner's accomplishment — but not the specific labels.

**Why these constraints exist:** Diátaxis says tutorials must inspire confidence through **perfect reliability** — every step must work, every time, for every reader. Choices, alternatives, and edge cases let unreliability in.

**What to avoid:**

- Choices the reader has to make on their own. A tutorial picks one path and walks it. Edge cases and alternatives belong in how-to guides or reference articles.
- Reference dumps mid-walkthrough. Link out to the reference article instead.
- "Why" detours. Trust the reader to learn the conceptual model later from an explanation article — link to it under *Before you start* or *Next steps*.
- Treating the article like a checklist. Tutorials are prose with embedded steps; they read like a guided session, not a recipe card.

## Worked example — *Getting started — running your first project*

> By the end of this tutorial, you'll have created your first project and you'll know the shape of the workflow: where to start a project, what the system asks for, what the result looks like, and what you do with it next. We'll do the whole thing once, end to end, so the next time you create a project you'll know exactly where you are in the process.

### Before you start

A few things to have in place before you begin:

- Your account is set up and you can sign in. If you can't, ask your administrator to invite you.
- You have a name in mind for the test project. For this tutorial, use a throwaway name — not a real customer or live project.
- You've had a quick read of the [permission roles reference](#) so you know whether your role can create a project.
- If you'd like the bigger picture before diving in, the [explainer on how projects fit into the workspace](#) takes about three minutes.

### Phase 1 — Find the workspace

Sign in and open the **Workspaces** tab from the main navigation. You'll see a list of workspaces ordered by most recent activity. Open the workspace you'd like the project to live inside.

You're now on the workspace overview page — this is where you'll spend most of your time when working in this workspace.

### Phase 2 — Create the project

On the workspace overview page, look for the **New project** button in the top-right corner. Click it. The system opens a form with a few fields pre-filled from the workspace's defaults.

Check that the defaults match what you'd expect — name, owner, visibility. If anything looks off, fix it now. When the form looks right, click **Create project**.

### Phase 3 — Read the result

The system creates the project and takes you to its overview page within a second or two. You'll see:

- **The project name** at the top of the page.
- **A summary panel** with the basic metadata — owner, visibility, created date.
- **An empty activity feed** ready for the first action.

For this tutorial, the project is ready to use. Click around the tabs to get a feel for the surfaces — *Tasks*, *Files*, *Members*, *Settings*. Each tab is the entry point for a different category of work.

### What you've learned

You've created a project from start to finish. You know where to launch one, what the system asks for, where to find the project overview, and what each of the main tabs is for. That's the whole loop for project setup — every project you create from here uses the same workflow.
